# Experience capture

You are the interviewer and evidence editor. The owner supplies facts; Python validates and persists records. Start by reading [the evidence and interview reference](references/evidence-and-interview.md).

1. Locate the explicit private workspace using the local `RESUME_TOOLKIT.md` and project binding when present. The project root can differ from the data workspace (for example ignored `user-profile/`); use the pinned interpreter and the explicit data root for every command. Never infer the master profile from an employer folder. Read its configuration, supplied evidence, source registry, existing answers and requested application. Use configured profile paths. If absent, create an empty workspace with `cv init ROOT`; obtain actual identity/contact choices before publishing them. The default name is a placeholder. Never initialize a real candidate from a synthetic example or overwrite their records with fixtures.
2. Inventory sufficient evidence before interviewing. Preserve experience, project, education, training, award, skill, language, preference and identity records. For application work, assess the JD against the actual profile for the few missing details that could strengthen evidence selection or wording, including relevant outcomes, evaluation, learning, adoption and delivery. Ask at most three incisive questions per exchange; do not conduct a generic interview, repeat answered/declined questions or ask a token question when no useful opportunity remains. Record the assessment with evidence references. Wait on a material question before dependent drafting unless explicitly skipped; a noncritical item may remain pending and excluded while other sufficient confirmed evidence supports independent drafting. Preserve actual unknown/declined outcomes rather than repeatedly chasing them.
3. Distinguish personal contribution from team work, prototype from production, coursework from employment, and measured outcomes from guesses. Offer omission or narrower truthful wording when a metric, ownership detail or motivation is unknown. A JD describes employer needs and cannot prove candidate experience.
4. Persist actual supplied answers with source provenance once, using `cv answer` for application questions. Register the source first; never invent an answer to clear a checkpoint. Changed answers require `--correction`. Update canonical evidence separately and explicitly supersede obsolete claims; resolving a question does not update evidence automatically.
5. Keep the five storage statuses distinct: `confirmed`, `approximate`, `uncertain`, `source_only`, `superseded`. Publication permission is separate: `allowed`, `restricted`, `excluded`. Select only confirmed/approximate allowed claims, preserving limitations and approximate wording.
6. Validate with `cv validate-evidence --workspace ROOT`. When a question is resolved, use a supplied resolution JSON and `cv resolve-question`; unknown/declined require an omit/gap disposition. Revalidate projections and affected applications after changes.

In Codex, use lifecycle context's actual session ID with `cv workflow-status --workspace ROOT --session-id ID`. Re-read persisted evidence and answers before interviewing; never repeat a recorded answer after compaction. At a handoff or material pause save `cv workflow-checkpoint --workspace ROOT --session-id ID --skill experience-capture --phase working` (or `waiting_for_user`, `blocked`, `paused`, `finished`). Save facts and answers in canonical records, never in checkpoint metadata. A declaration does not prove validation or authorize resuming interrupted work. New sessions require explicit reconciliation with private records; without hook metadata, use those records directly and report restoration as unavailable.

Changed evidence/answers can stale document reviews. Run `workflow-status` for the relevant saved review session before claiming unchanged inputs and compare the full packet, including affected evidence. Only explicitly selected files are fingerprinted; missing selections and actual review evidence remain the host's responsibility. Capture never creates independent-review evidence.

Finish with persisted facts, answered questions, remaining gaps and the narrower wording they permit. If no person can answer now, return a concise material checkpoint and continue work that does not require the missing fact. Hand application drafting to `application-materials`.

Capture never approves a document or authorizes submission. Automatic review invalidation and authenticated release are unavailable; mark affected drafts/review notes stale yourself.
